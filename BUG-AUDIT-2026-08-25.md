# Free + Pro bug audit — 2026-08-25

Scope: `optionbay-product-options-addons-woo` (Free) and
`optionbay-product-options-addons-woo-pro` (Pro), read at HEAD. Every finding
below was traced in the source; nothing is carried over unverified from the
stale `errors.md` / `qa_audit.md` in the Pro repo. **No code was changed.**

**Scope of the read.** I concentrated on the Free/Pro coupling seams and the
cart → pricing → inventory pipeline: `CartManager`, `InventoryManager`,
`PricingEngine`, `AddonRenderer`, `ConditionEvaluator`, `FieldFactory`, the
save/validate/sanitize path in `AddonGroupController`, `ApiController`'s
permission layer, `assets/js/frontend.js`, and all of Pro's `app/` plus
`src/pro-extensions.tsx`. **Not read:** `ResourceController`,
`SettingsController`, `Core\Settings`, `Core\Cron`, `Exporter`, most of
`DbManager`, the 13 concrete `app/Fields/*` classes, and roughly 800 of
`AddonGroupController`'s 1296 lines. Silence about those is absence of
inspection, not a clean bill of health.

Re-verified and now **fixed** (so not listed as bugs): the swatch-exclusion trio
in `CartManager`, the `PricingEngine::calculate()` missing-`$config` call site,
the `restore_inventory_stock` vs `restore_order_stock` callback mismatch, the
`opopw_allowed_field_types` / `FieldFactory` two-gate drift, and the
field-level Pro schema keys (`formula`, `max_file_size`, …), which Pro now
preserves through `opopw_validation_rules` + `opopw_sanitize_field`.

---

## High

### 1. Option-level Formula pricing can never be saved — the option prices at 0

Free offers Pro's price types on **per-option** price selects, but there is no
persistence path for the option's formula string.

- `src/components/addonBuilder/constants.ts:80` — `PRICE_TYPES` is built through
  `applyFilters('opopw_price_types', …)`; Pro appends `formula` and
  `character_count` (`pro-extensions.tsx:54-64`).
- That same `PRICE_TYPES` array feeds the **per-option** selects at
  `src/components/addonBuilder/OptionEditor.tsx:358` and
  `OptionEditorAccordion.tsx:215`.
- `app/Api/AddonGroupController.php:1108-1165` has no
  `schema.*.options.*.formula` rule, and Pro's `add_pro_validation_rules()`
  only registers `schema.*.formula`. rakit's `getValidData()` drops unruled keys.
- `sanitize_schema()`'s per-option allow-list
  (`AddonGroupController.php:892-907`) is a closed literal with **no**
  `apply_filters` — there is no `opopw_sanitize_option` counterpart to the
  per-field `opopw_sanitize_field` at `:977`.
- `CartManager.php:585` correctly passes `(array) $opt` into
  `PricingEngine::calculate()`, and `FormulaStrategy::calculate()` reads
  `$config['formula'] ?? ''` → empty → `return 0.0`.

**Effect:** a merchant sets a select/radio/checkbox option to "Formula-based
Pricing", the *type* persists, the expression does not, and the customer is
charged nothing for that option. Silent revenue loss, no error anywhere.

Fix shape: add `schema.*.options.*.formula` to Pro's rules, and add an
`opopw_sanitize_option` filter in Free's option loop for Pro to hook.

### 2. "Formula-based Pricing" is unusable on every field except the `formula` field type

`pro-extensions.tsx:68-86` renders the "Math Formula" input **only** when
`fieldDef.type === 'formula'`. But the `formula` *price type* is offered on
every field (`src/components/addonBuilder/FieldRow.tsx:465`). Pick a Text,
Number or Date field and set its pricing to Formula → there is no input
anywhere to enter the expression → `formula` stays `''` → `FormulaStrategy`
returns `0.0`.

Fix shape: gate the settings row on `fieldDef.price_type === 'formula'` as well
as on the field type.

### 3. File field: `allowed_types` vs `allowed_extensions` key mismatch, and no admin UI for either

- Pro's defaults write `allowed_extensions` and `max_file_size`
  (`pro-extensions.tsx:117-120`).
- `FileField::render_input()` (`FileField.php:34`) and `FileField::validate()`
  (`FileField.php:93`) both read **`allowed_types`** — a key nothing ever
  writes — so both always fall back to the hardcoded `'.jpg,.png,.pdf'`.
- `CartExtension::process_field_value()` (`CartExtension.php:113`) papers over
  it with `allowed_types ?? allowed_extensions`, which is why uploads still
  work — but it reads a *different* value than the two above.
- Worse: `opopw_field_settings` adds **nothing** for `type === 'file'`
  (`pro-extensions.tsx:67-111` only handles `formula` and `enable_stock`), so
  the merchant has no UI to change allowed extensions or max file size at all.

**Effect:** the File Upload field is permanently locked to jpg/png/pdf and 5 MB,
and the `accept` attribute, the client-side hint text, and the server-side check
are reading a key that is never populated.

### 4. Pro has no license gating whatsoever

`OpopwPro\Core\Plugin::run()` (`app/Core/Plugin.php:106-108, 157-161`)
instantiates `CartExtension`, `FieldExtension` and `SettingsExtension`
unconditionally. `LicenseManager` exposes only `activate()`, `deactivate()`,
`init_update_checker()`, `mask_license_key()` and
`admin_notice_license_inactive()` — there is **no** `is_active()` / status
accessor, and `grep -rn "is_active\|is_license\|has_valid" app/` returns zero
hits outside the license files themselves.

**Effect:** installing the Pro zip with no license key unlocks File Upload,
Formula/Character-Count pricing and formula stock reduction in full. The only
consequence is a dismissible admin notice.

## Medium

### 5. Cancel → reinstate → cancel permanently double-deducts add-on inventory

`restore_order_stock()` early-returns when `_opopw_stock_restored === '1'`
(`CartManager.php:751`) and sets that flag at `:779`, but
`reduce_inventory_stock()` never clears it. WooCommerce *does* reset its own stock-reduced flag on cancel — verified at
`woocommerce/includes/wc-stock-functions.php:153-156`, where
`wc_maybe_increase_stock_levels()` calls `set_stock_reduced( $order_id, false )`
and is hooked to `woocommerce_order_status_cancelled` (and `…_pending`). So the
next transition back to processing fires `woocommerce_reduce_order_stock` again
and we decrement again — while our stale flag blocks the second restore. Every cancel/reinstate cycle leaks stock
out of the pool with no way to notice.

Fix shape: `$order->delete_meta_data('_opopw_stock_restored')` inside
`reduce_inventory_stock()`.

### 6. Refunded orders never restore add-on inventory

`CartManager.php:82` hooks only `woocommerce_order_status_cancelled`, though
`restore_order_stock()`'s own docblock says "cancelled **or refunded**". Refunded
orders therefore never release their add-on inventory. The same gap applies to
`woocommerce_order_status_pending`, which WooCommerce *does* treat as a restock
trigger for product stock (`wc-stock-functions.php:156`) but which we don't hook.

(For accuracy: WooCommerce does not auto-restock on refund either — that only
happens when the admin ticks *Restock refunded items*, via
`wc_restock_refunded_items()`. The bug here is the mismatch between this
plugin's own documented intent and its hook list, not divergence from core.)

### 7. `InventoryManager` re-implements reduction math without the extension filter

`InventoryManager::calculate_intent_reduction()` (`InventoryManager.php:361`) is
a private copy of `CartManager::calculate_reduction_amount()` **minus** the
`apply_filters('opopw_calculate_reduction', …)` call. So `get_cart_reserved_stock()`
ignores Pro's `formula` reduction mode entirely: the availability check and the
actual decrement compute different numbers for the same intent.

### 8. `collect_intents_from_request()` passes `null` where an intent array is expected

`CartManager.php:876` and `:890` call
`calculate_reduction_amount( $quantity, $mode )` without the third `$intent`
argument, so it defaults to `null`. Pro's `calculate_reduction()` then evaluates
`$intent['formula']` on `null` → a PHP 8 *"Trying to access array offset on
value of type null"* warning, and the pre-add-to-cart stock check silently falls
back to plain quantity instead of the formula amount.

### 9. `decrement_stock()` reads "0 rows affected" as failure → hard checkout crash

`InventoryManager::decrement_stock()` (`:220-245`) returns
`(bool) $wpdb->query(...)`. MySQL reports 0 affected rows when an `UPDATE`
changes nothing — i.e. whenever `$amount` is `0`. Pro's
`evaluate_reduction_formula()` returns `max(0, …)` (`CartExtension.php:243`), so
a formula legitimately yielding 0 is reachable. `reduce_inventory_stock()`
(`CartManager.php:723-732`) then throws
`\Exception('Insufficient stock…')` on `woocommerce_reduce_order_stock`,
failing an otherwise-valid order.

Fix shape: `return false !== $result;`, plus an early return when
`$amount <= 0`.

### 10. Live price preview is wrong for both Pro price types and for any negative price

All in Free's static `assets/js/frontend.js`, which Pro does not replace:

- `computePriceByType()` (`:427-436`) handles only `flat` and `percentage`;
  `default: return amount`. A `character_count` field shows the *per-character
  rate* as the whole delta; a `formula` field shows the (unused) configured
  amount. Both disagree with what the server charges.
- `calculateOptionPrice()` (`:277`) gates on `parseFloat(opt.price) > 0`, so
  **negative** option prices (discount options) never appear in the preview even
  though `PricingEngine` applies them — its short-circuit only triggers on
  exactly `0.0`. Formula/character-count options with no `price` are skipped too.
- `updatePriceDisplay()` (`:446`) hides the total element outright when
  `addonTotal <= 0`, so a net discount renders as nothing at all.

### 11. Pro's admin bundle is enqueued on every wp-admin page

`SettingsExtension::enqueue_admin_scripts( $hook )`
(`SettingsExtension.php:58`) accepts `$hook` and never looks at it —
`build/pro-extensions.js` is enqueued unconditionally across all of wp-admin.
Free does this correctly, bailing on `! $this->is_menu_page()`
(`Admin.php:215-217`).

### 12. Frontend CSS/JS are cache-busted with `time()`

`AddonRenderer.php:411` and `:419` pass `time()` as the `$ver` argument for
`assets/css/frontend.css` and `assets/js/frontend.js`, producing a brand-new URL
on every single request. No browser or CDN can cache either file, and it is a
standard WordPress.org review flag.

## Low / hygiene

13. `$files_data` is pulled out of `$_FILES` and never used, in both
    `CartManager::validate_add_to_cart()` (`:169`) and `add_cart_item_data()`
    (`:402`). The latter's docblock still claims it "handles … WordPress native
    file uploads" and `@throws` on upload failure — that logic moved to Pro's
    `CartExtension` and the docblock was left behind.
14. `CartManager.php:519` — `$_add_to_cart = apply_filters( 'opopw_ajax_calculate_totals', true );`
    assigns to a variable that is never read, so the documented filter has no
    effect on anything.
15. `foreach ( $field_schema['options'] as $opt )` has no `?? array()` guard at
    `CartManager.php:455` and `:889`, while the equivalent loop in
    `calculate_totals()` (`:573`) does. A choice field saved without options
    emits a PHP 8 warning on add-to-cart.
16. **Latent, no consumer today:** `opopw_product_group_ids` is applied at exactly
    one site — `AddonRenderer.php:400`, inside `maybe_enqueue_assets()`. It is
    *not* applied in `render_product_options()` (`:83`),
    `CartManager::get_groups_for_product()` (`:96`), or
    `collect_intents_from_request()` (`:864`). Nothing currently hooks it
    (Pro's only copy is in its dead `AddonRenderer` fork), and **Pro's targeting
    exclusions are not affected** — those resolve through the `is_exclusion`
    column in `DbManager::get_groups_for_product()`, which correctly subtracts
    excluded groups before anything downstream sees them. But if anything ever
    does hook this filter, it will suppress only the CSS/JS/hydration while the
    fields still render, validate and price — leaving unstyled markup with no
    conditional logic, which is worse than either extreme.
17. Option-level **Price per Character** charges by the length of the option's
    stored `value` slug: `CartManager.php:585` passes `$val` (the option value)
    as `$field_value`, and `CharacterCountStrategy::calculate()` returns
    `mb_strlen( (string) $value ) * $amount`. An option valued `red` at $0.50/char
    silently costs $1.50. Same family as finding 1 — Pro's price types are
    offered on per-option selects without the per-option semantics existing.
18. Pro ships dead forks of Free classes, none registered in `config/core.php`
    or referenced anywhere: `app/Core/AddonRenderer.php`, `app/Core/AddonGroup.php`,
    `app/Core/Importer.php`, `app/Pricing/PricingEngine.php`,
    `app/Pricing/{FlatFee,Percentage}Strategy.php`,
    `app/Helper/{WooCommerce,ConditionEvaluator}.php`, plus
    `assets/js/frontend.js` and `assets/css/frontend.css`. `AddonRenderer.php`
    is byte-identical to Free's apart from ~28 namespace lines, so Free-side
    fixes silently diverge from it. Also leftover CampaignBay branding in
    `assets/img/campaign_bay.svg` and `dash_icon_campaign_bay_{dark,light}.svg`.
19. Pro's header reads `Plugin Name: Smart Product Options and Addons` while the
    codebase, its own admin notices and Free's upgrade URL all brand it
    "OptionBay". Stale `.pot` files in both repos:
    Free's `languages/product-options-addons-woo.pot` (still
    `Project-Id-Version: … 1.0.0`) alongside the current
    `optionbay-product-options-addons-woo.pot`, and Pro's
    `smart-product-options-addons.pot` alongside
    `optionbay-product-options-addons-woo-pro.pot`.
20. `OPOPW_DEV_MODE` and `OPOPW_PRO_DEV_MODE` are both hardcoded `true` and read
    nowhere in either codebase — dead constants. (Logging is gated on the
    `debug_enableMode` setting instead, which is correct.)
21. `errors.md` and `qa_audit.md` in the Pro repo describe a
    `OpopwPro\Core\CartManager` and `OpopwPro\Core\Preloader` that no longer
    exist — their line references point into a pre-refactor tree and will
    mislead the next reader.

## Docs impact

Per `CLAUDE.md`'s docs rule, findings 1–3 change documented behaviour of the
Pro feature set. If they are fixed, the following pages under
`/home/sdd/Documents/campaign-bay-testing/docs/optionbay/docs` likely need
updating: the pricing-strategies page (formula pricing scope: field-level vs
option-level), the field-types page (File field's configurable extensions and
size limit), and the inventory/stock page (formula reduction mode).
